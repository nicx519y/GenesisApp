# 自动化测试平台协作规范

保留已有未提交改动；按变更范围运行相关测试和类型检查。

## Case 节点与 QA 埋点处理规范

- 每次处理节点先查询 QA 埋点库，核对对象、属性、范围、操作、参数、清理要求及执行环境；记录复用或不复用依据。已有有效实现优先复用，候选先验证后修复，无可复用实现才新增。不得按 Case 复制同一埋点。
- 新建及本次修改的独立埋点必须物理隔离：App 使用 lib/app/qa/hooks/<稳定埋点ID>/，App 专属测试使用 test/app/qa/hooks/<稳定埋点ID>/；QA 适配与测试放在 runners/ 下的 hooks/<稳定埋点ID>/。目录 ID 将冒号编码为 %3A，其他稳定 ID 字符保持不变。一个目录只归属一个埋点；未修改的历史实现不要求批量迁移。
- 通信、鉴权、调度、公共测试工具可以共享；公共入口仅注册和分发，不堆入具体埋点业务分支。保留真实共享依赖和版本指纹。已存在的共享文件只允许必要注册接线或移出被拆分的逻辑。
- 出错后必须阅读完整错误、命令输出和验证报告，在同一候选工作区修复并重验，不设固定修复轮数。用户停止、服务中断或必须人工解决的阻碍才结束；不把重复失败本身当成人工阻碍。
- 当前节点所选环境必须有真实观测、正反例、必要清理和构建身份；不得用其他环境通过替代，不得修改业务预期、伪造证据或弱化验证器来获得通过。
- 候选必须通过复用依据、文件归属和修改边界校验；发布必须通过审核及源码一致性校验。停止后不得继续发布；不得重置其他节点或改写其他 Case 的业务计划与绑定。

- 节点 AI 的最终交付是可重复执行且保持业务预期的工程测试实现。每次执行失败须结合日志、截图、页面树和历次方案重新诊断，落实新方案；AI 自身执行失败也属于诊断输入。通过结构化结果区分已修复、待继续修复、必须人工处理；退出码为 0 不代表修复成功，未落实修复不得重跑原验证。

## V3 Case 检查点与埋点分层
- 埋点库仅提供可复用标识、观测与原子操作；Case 步骤、参数、业务预期、依赖和清理由 Case 拥有。埋点契约通过不是 Case 节点通过。
- Case 专属实现放在执行器 cases/<caseId>/nodes/<nodeId>/，不得写入 hooks/<hookId>/ 或公共 bridge。复杂脚本只可经受控上下文调用已声明能力，不可修改预期或验证证据。
- 节点验证必须在本次同一会话中执行起点至目标的前缀，禁止偷用上次状态、隐式重启、在只读埋点内补导航或重复准备。前序失败阻塞下游，资源在运行结束统一清理。
- AI 先判断失败属于原子能力还是 Case 逻辑，只修改相应归属；业务顺序或预期变更必须形成可确认的修订草稿。
- 发布分别校验埋点契约、Case 前缀及完整 Case 证据、源码指纹和运行身份；旧证据不得升级冒充 V3 证据。

- Case 业务方案由 AI 根据原 Case、现有步骤及埋点库先生成完整可编辑草稿；迁移说明自动产生，合理歧义附带建议与依据，用户可直接审核或修改。不能将编写迁移说明和工程步骤转交用户；只有无法从资料确定的必要业务事实才留作待补充。用户改文案后必须重新同步结构化步骤，未确认草稿不得执行或宣称验证通过。

## 业务与框架职责边界（覆盖旧的笼统清理要求）
业务方案只描述目标、前提、操作、预期、确有必要的业务数据恢复；标题最多40字，业务说明最多160字。埋点复用依据、缺口和诊断保存为独立工程记录，不写进业务正文。不得截断内容或合并独立断言来缩短文字。
会话关闭、连接/子进程/设备占用释放由框架统一执行，不生成 case.execution.resources 业务检查点；真实业务恢复仍须声明并登记资源。只读身份检查不得隐含清除身份，首启引导须单独获得业务授权。
展示文案、确认控件及类型声明不属于执行指纹；操作、参数、断言、依赖、脚本、埋点版本及真实运行依赖仍须校验。历史证据不得重写或自动批准。

源 Case 与已确认计划的关联校验必须比较已存档原文的业务字段；原文需以原始哈希校验，不得用修订后的 plan.spec 冒充源快照。标题、版本号、标签、优先级变化不要求重新迁移；业务描述变化须有明确等价依据，无法证明时列出差异要求确认。兼容检查不得改写原计划、历史证据或自动发布。

Android 安装包按 App 源码、依赖、资源、构建配置和工具链指纹复用；测试脚本和文案变动不触发打包。构建身份和桥接认证归属安装包，运行标识与实例身份每次独立核对。契约测试与 Case 前缀可复用同一 APK，但不可沿用契约准备状态；完整 Case 内共用会话，最后统一清理。

## App 就绪属于框架准备
普通 Case 执行前由框架保证 App 已启动且完成首帧；未启动时启动，已就绪则直接复用本次会话，不逐节点重启。不生成“检查 App 已启动”的业务检查点，不为此建设或审核共享埋点。只有 Case 明确测试启动操作、启动失败、首帧耗时等业务行为时才保留对应步骤和断言。系统准备失败阻塞业务步骤并保留就绪观测与必要清理回执；组件测试不能冒充 App 就绪证据。自动启动不授权登录、清除身份、完成首启引导或修改业务数据。历史普通启动前提由兼容投影交给框架，保留原计划和稳定节点 ID；引用其输出或有特殊行为的节点不得静默删除。

## 公共个性化测试环境准备
普通 Android mock Case 通过带版本的环境配置预置已完成引导状态，不重复生成性别、年龄、提交或跳过订阅业务节点。首次引导 Case 显式使用 first_run，preserve 不修改资料。运行固定配置，在启动屏障前通过受鉴权的 internal debug QA 接口准备；必须核对 App 实际读取结果和本次恢复回执。准备只影响当前 mock 身份资料，不登录、不清除身份、不支付、不关闭未知弹窗。配置运行时传入，不能因切换资料重新构建。已有计划以未确认修订迁移，旧证据不升级，新通过证据不得代替业务审核。

## Case 级默认操作
普通使用以完整 Case 为单位处理、验证和审核，不要求用户逐节点点击。业务检查点按顺序共享本次会话，节点级处理仅在高级调试中提供，并明确其独立会话与前缀重放成本。运行已发布 Case 与 AI 建设分离：回归运行不生成埋点、不改脚本、不自动修复或发布，失败保留报告，用户可发起整条 Case 修复。每次处理保存实际开始和结束时间，总耗时包含修复重验、不含排队，终止后固定显示；不能用最后一轮验证时间冒充总耗时。

## 契约验证效率
先收集并合入 Case 所需候选，再按最终源码、契约版本及环境筛选真正失效的契约证据。有效证据可跨任务复用，但不自动发布或替代本次 Case 执行。兼容的契约测试共用一次准备、导航及后台往返；各埋点仍在独立模块中记录真实正反例及恢复观测。不兼容的契约不能强行合并。契约会话与业务 Case 会话隔离；同一完整 Case 中不得逐节点启动 App 或重放前缀。

## 独立健康监控与 Issue 修复
健康监控与 Case/埋点执行分离。结构化心跳、真实观测、阶段推进、候选校验才是进展；重复日志和口头声明不算。采用任务开始时固定的规则版本。
规则升级的异常先记录本地 Issue，再停止受影响任务。必须确认进程退出与本次资源清理回执，缺失回执不得自动恢复，禁止无条件清除身份。首次上线仅观测，不接管历史运行。
Issue 分析只读；修复在独立候选内进行。严禁修改健康规则、验收器、业务预期、原始证据或审核状态来获得通过。App 业务代码禁止由平台修改；App QA 埋点、桥接及专属测试仅限 lib/app/qa/、test/app/qa/，独立验证通过后默认自动处理，Settings 可开启 App QA 审批；业务变更必须生成修订。日常回归业务失败只记录问题，不自动改测试。
平台独立执行根因回归测试及相关检查后才能应用修复；候选和源码基线出现冲突时保留现场。用户停止取消后续自动恢复；服务重启需重新核对资源。恢复新建运行并重放原完整 Case 或原前缀，不复用设备会话，不自动发布。
本节覆盖原“无限重试”要求：已启用健康接管的任务按冻结规则升级独立 Issue；独立修复连续两轮无可验证进展转待人工，不递归启动修复 Agent。

回归运行资格与旧证据有效性分开校验：固定计划引用的已审核埋点版本在所选环境曾有有效发布记录，即可执行新的完整 Case；源码变化使历史证据失效，不等于撤销发布。必须检查发布契约、实现版本、环境和文件存在性；未发布、已退役、记录不完整或版本不匹配仍阻塞。不得把旧证据改成通过，建设和审核发布仍要求当前源码的有效证据。

健康自动模式启用后，失败边界必须先同步判断接管，再允许原 Agent 开始下一轮；5 分钟无进展只发任务告警，达到停止阈值的 Issue 必须拥有停止流程，不能建完 Issue 继续原操作。原会话清理确认后才能进入独立修复；同一设备平台的其他执行任务等待，无关主机任务不受影响。每次恢复使用新的清理回执，不能沿用原任务回执；迟到监控事件不得回退修复状态。历史观测任务和用户主动停止的链路不自动重新启动。运行器修复通过独立检查后可自动应用并恢复；需要平台重启、App 或业务修改时明确转审核或待处理，不绕过现有边界。

## Issue 自动接管设置
Settings 的独立「Issue 自动化」区域提供自动接管开关，默认开启，切换即持久化。用户明确关闭的设置必须保留，不能被默认值覆盖；关闭后新任务仅观测和记录 Issue。任务冻结启动时的规则，切换不追溯接管历史 Issue，也不更改运行中的任务。高级阈值单独保存，切换开关不能意外提交未保存的阈值。历史上线验收记录继续留档，正常开关不再依赖人工写入 rollout 标记；清理、权限、审核及恢复校验始终保留。

## Issue 工程修复与人工决策边界
原始任务、候选定义、修改前基线、文件差异、历次修复与报告必须通过持久化关联交给 Issue 分析，缺失材料先由平台收集。原因不确定不等于越权，不得把工程调查交给业务用户。建设阶段的测试实现或 App QA 候选可在已停止任务的隔离工作区中继续修复；必须保护原始基线、校验器和历史证据，新增根因测试并由平台独立验证。App QA 候选验证通过后按 Settings 决定是否审批，默认自动恢复隔离 Case 验证，主工作区应用与发布仍走 Case 审核。已发布回归中的真实业务失败不得自动改预期。材料缺失、工程修复无进展、业务决策分别说明原因与下一步，不统一写“超出自动修复权限”。

Issue 接管停止候选时必须创建新运行标识，保留原运行停止状态并拒绝其迟到写回。先由平台验证保留候选，确认真实失败后才让 AI 修改；AI 只提交候选，不反复尝试 SDK、设备或完整验证命令。修复任务必须接入同一心跳、命令和清理遥测，其自身异常追加原 Issue 并安全停止，不递归新建 Issue。排队原因以调度器资源占用为准；恢复时合并相同计划、环境和范围的排队请求，保留原候选恢复步骤。诊断 JSON 按值脱敏后重新编码，保留原始来源哈希，不改写历史归档。


## 平台控制的工程修复交接

- 构建控制器提供 `candidate-layout.json`，固定稳定埋点 ID、独立目录和共享入口边界。生成 Agent 按布局实现，公共桥接仍只注册和分发；实际逻辑迁移由 Agent 在原隔离候选完成，不能绕过文件归属校验。
- 所有权和编译阻塞通过结构化工程诊断交接：违规路径、允许目录、修复策略、必跑检查与不可修改边界。读取 `engineering-diagnostic.json` 和完整命令报告，不能把工程校验失败解释为需要用户编写代码或改变业务方案。
- 已声明真实依赖中、位于同一稳定埋点专属目录且没有其他归属的文件，控制器可补齐 `implementationFiles`。不自动认领共享文件、不猜测新依赖、不改变源代码或契约；补齐动作保留记录并继续原有归属校验。
- 必须先通过构建前检查，再启动设备契约验证；失败保存完整诊断并进入候选修复，不重复启动 App 来等待一个无法编译的候选。
- 每个候选验证成功立即持久化独立回执。后续候选失败重试时，核对候选版本、审核内容、实际源码与共享依赖指纹，仅重做失效部分。已批准但发生变化的候选重新验证；App 差异仍需审核，不能沿用旧批准。
- 只有新增独立通过的检查才算修复进展，重复日志和相同检查不算。连续无进展受健康规则约束；停止原因区分用户、健康监控和服务关闭，旧记录缺少来源时不推断为用户操作。
- App 候选可以在隔离区修复并验证；审核发生在具体差异和验证结果生成以后、应用 App 修改以前。平台工程修复和 App 修改审核分别表述，不以含糊的“等待应用修改授权”阻塞整个工程诊断。

## App QA 权限与审批（覆盖旧的 App 全量审批规则）

- App 写入范围严格限于 `lib/app/qa/`、`test/app/qa/`；业务组件、页面、入口、构建配置及其他 App 路径不可写。不能把业务文件改动命名为 QA 接线来放行，审批开关也不能扩大此边界。只读业务源码及真实依赖指纹仍保留。
- Settings 的「App QA 改动需要审批」默认关闭。QA 候选必须完成独立验证和清理；关闭时自动接纳、应用允许范围内的改动并继续处理，开启时展示具体 QA 差异等待审批。既有显式设置须持久化；模型保存不得覆盖审批偏好。
- 生成 Agent 的 App 可写目录也限制到上述两处，输出材料使用独立小目录，不把包含整个 App 候选的父目录加入写入权限。应用时校验真实路径，拒绝符号链接逃逸。业务方案改变仍形成待确认修订，禁止用取消审批绕过业务预期或证据校验。
- QA 观测可通过已有接口、实际 UI 渲染与现有日志在 QA 模块实现；缺少业务接入点时先找不改业务源码的观测方式，不能在页面或公共业务组件补标记。历史越界候选保留归档并恢复业务文件基线，重建 QA 专属实现与真实证据。

建设恢复中出现新的埋点/契约工程故障，在同一 Issue 内等待当前进程退出和真实清理回执后串行修复；不创建递归 Issue，不并发抢占候选，保留冻结的相同失败停止阈值。回归运行、业务预期失败、身份或证据异常、用户停止、资源清理缺失仍禁止自动续跑。

## 公共测试数据来源规则

- 业务状态、测试数据来源、工程能力分开建模。涉及身份、数据集、资源或外部系统前提时，生成方案须声明结构化 dataRequirements，先询问 Mock 模拟、已有真实数据或受控新建方案；用户明确答案不可由 AI 建议自动填写。
- 选择 Mock 不要求真实账户；选择已有真实账户才收集账户名/用户 ID 及已有授权接入引用，不收集密码和令牌。不同来源按选择显示必要信息；未选方案或缺少信息不能确认/执行。
- 数据来源按明确选择与执行环境核对。Mock 不能冒充真实系统证据；来源改变须生成待确认修订，修复 Agent 禁止切换。准备/恢复能力缺失是工程待办，不能擅自索要真实账号、改变断言或清空用户数据。仅读取既有真实前提时，前提不符应报告而非自动改造用户状态。

## 生成前确认与平台 Issue 边界

- 规划分为“识别待确认信息”和“生成执行检查点”。前者只输出业务概述、问题与数据来源选项，不输出节点、绑定、脚本；必要选择和信息须由用户明确确认后，后者才能开始。AI 推荐不可自动填写任何需要确认的回答。后续发现新业务假设时返回确认阶段，不交付可执行检查点。
- App 观测与业务预期不符、指定真实账号或资源不满足测试前提，是测试未通过，保留当前报告、阻塞下游并正常清理；不进入平台 Issue，不启动自动修复或偷偷修改用户数据。测试平台 Issue 只管理框架、埋点工程、执行器、证据和清理等平台故障。
- 只有本次运行、完整身份与调用观测、独立重算失败断言及成功清理都有效，才能标记为普通测试失败；证据缺失/异常、清理失败和执行器超时不能靠测试失败标签屏蔽。平台修复后的恢复运行若产生合法 App 测试失败，关闭平台故障的恢复占用并将测试失败保留在 Case 报告。

## 工程监督 Agent

用户要求的工程监督层可在原 Issue 修复受阻后继续调查和交接，覆盖旧“转待人工即结束”的工程处理限制。监督器每个 Issue 使用持久会话；相同证据不重复触发，自动介入有上限。正常排队、普通业务失败、用户停止和仅观测任务不接管。首次启用仅处理新 Issue，历史问题由显式监督请求进入。

监督调查只读，工程执行由控制器按新租约串行接管。平台维护候选可修调度、接管、恢复、环境准备与公共能力接线；必须新增根因测试、独立验证并展示具体差异，应用仍按平台审核和重启路径。不得修改监督器权限、健康规则、验证器、业务预期、旧测试或历史证据来获得通过。用户停止、实际进程退出、清理回执、App QA 路径边界与发布审核继续有效。监督器自身失败不递归新建 Issue 或无限启动 Agent。
